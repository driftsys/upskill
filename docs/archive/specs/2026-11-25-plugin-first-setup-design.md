# Plugin-first setup design

Date: 2026-11-25. Status: **approved by the user on 2026-11-25; implemented on
branch feat/plugin-first-setup**. Decision record:
[AD-0047](../../adr/0047-plugin-first-setup.md). Related records:
[AD-0044](../../adr/0044-plugin-output-of-a-bundle.md),
[AD-0046](../../adr/0046-plugin-mvp-components.md),
[plugin MVP design](../../wip/specs/2026-11-24-plugin-mvp-design.md).

This document is a design. It does not describe released behaviour.

## Intent

Make one plugin, `upskill@metapowers`, the single way to set up upskill in
Claude Code and Copilot CLI. Installing the plugin gives the user:

1. the upskill skills;
2. a session-start hook that offers to install the `upskill` CLI when it is
   missing;
3. the existing update notice for content installed with `upskill add`;
4. a notice when a newer `upskill` CLI release exists, with the command that
   installs it.

Why: today the setup takes three unconnected steps (run `install.sh`, add the
marketplace and install the notice plugin for each client, run
`upskill add driftsys/upskill`). The user wants one entry point.

## Goals

- G1. One plugin install per client gives the skills and the hook.
- G2. The plugin is generated by `upskill pack` from a bundle in this
  repository. The hand-copied plugin in `driftsys/metapowers` goes away.
- G3. The skill `upskill-cli` is renamed `upskill-managing-content`, because
  users read `upskill-cli` as the name of a second program.
- G4. When the CLI is missing, the hook tells the user how to install it.
- G5. When a newer CLI release exists, `upskill update --notice` prints one line
  with the install command.
- G6. `install.sh` tells the user how to install the plugin.

## Non-goals

- No `upskill self-update` command. Running `install.sh` again is the update
  path.
- No change for opencode users: they keep `install.sh` plus `upskill add`.
- No check for plugin updates. The clients update plugins themselves
  (`claude plugin update`, `copilot plugin update`, marketplace auto-update).
- No back-compatibility for the old skill name or the old bundle name (no alias,
  no migration); upskill is before 1.0.

## Anti-goals

- The hook must never download or install anything by itself. It only prints.
- The hook must never block or slow a session start: `--notice` keeps its
  contract (exit 0 in every case after argument parsing, nothing on stderr, a
  bounded run time).
- A failed network request must print nothing, not an error.

## Constraints

- `pack` writes the plugin name from the bundle name. The plugin must be named
  `upskill`, so the bundle must be named `upskill`.
- `pack` already writes a notice hook entry into every plugin whose bundle has
  rules. Its bytes come from `plugins/` through `include_str!`
  (`src/pack/hooks.rs`). That entry is shared by every third-party plugin with
  rules, so it must not gain upskill-specific install messages.
- `update --notice` does not fetch content; the existing update check uses
  `git ls-remote` (`src/pipeline/check.rs`).
- Copilot CLI gives hook output to the model, not to the user. The Copilot hook
  uses `--repeat` and asks the model to tell the user.
- Binary size target about 3 MB; no new dependency.

## Approaches

Where the CLI update check lives:

1. **In the CLI, inside `upskill update --notice` (chosen).** Rust code with
   tests, reuses the notice cache and its once-only rule, and every hook that
   already runs `--notice` gets the line for free.
2. In the hook script, with `curl` on the GitHub API. Rejected: version logic in
   shell, a dependency on `curl`, two copies (one per client), no shared cache.
3. Approach 1 plus `upskill self-update`. Rejected for now: binary replacement,
   checksum and atomic-rename code, and a second install path beside
   `install.sh`.

The user chose approach 1 on 2026-11-25. The user chose the CLI release (not the
plugin version) as the thing to check, on the same date.

## Design

### D1. Rename the skill

`skills/upskill-cli/` becomes `skills/upskill-managing-content/`, with the same
`name:` in its frontmatter. Update every mention: the bundle, the other skills,
`AGENTS.md`, `docs/book/`, the README. An existing install keeps `upskill-cli`
until an `update` of that source removes it as gone from the source; a test pins
that behaviour.

### D2. Rename the bundle

`skills/prompt-engineering.bundle.yaml` becomes `skills/upskill.bundle.yaml`
with `name: upskill`, so `pack` writes a plugin named `upskill`. Its items keep
the seven skills. Its `plugins:` section (superpowers) is unchanged.

### D3. The setup hook item

A new command hook item, `skills/upskill-setup/HOOK.md`, listed in the bundle
under `items.hooks`. It has one event, `session-start`, with a `run` script
(`upskill-setup.sh`, executable) and a timeout of 30 seconds. No matcher for
either client: the hook format cannot give Claude Code `startup` and Copilot CLI
no matcher (`src/pack/hooks.rs`), and running also on resume, clear and compact
is harmless because each notice prints once and the missing-CLI message prints
once a day. _(Designer call, made in the plan.)_

The script reads `UPSKILL_CLIENT` (`claude` or `copilot`, set by `pack`):

- When `upskill` is not on `PATH`: print the install message (below) at most
  once per day. A marker file `<cache>/upskill/setup-offered` (`$XDG_CACHE_HOME`
  when absolute, else `~/.cache`) holds the date of the last message; the script
  writes it with plain shell. _(Builder call made by the designer: once per day,
  so a user who postpones is reminded but not on every session.)_
- When `upskill` is on `PATH`: run `upskill update --notice` (Claude Code) or
  `upskill update --notice --repeat` (Copilot CLI), and print its lines.
- Output format per client is the one the current notice plugins use: Claude
  Code gets `systemMessage` plus `hookSpecificOutput.additionalContext`; Copilot
  CLI gets `additionalContext` that starts with "Tell the user at the start of
  your first reply:". The JSON escaping is the one in the current
  `plugins/*/hooks*.json` commands.
- Every failure path exits 0 and prints nothing.

Install message text:

```text
The upskill CLI is not installed. Install it with:
curl -fsSL https://raw.githubusercontent.com/driftsys/upskill/main/install.sh | sh
```

On Copilot CLI the model receives this text and may offer to run the command;
running it stays the user's decision through the client's own command approval.

The bundle has no rules, so `pack` adds no built-in notice entry: the setup hook
is the only session-start entry, and the notice runs once.

### D4. CLI release check in `update --notice`

After the lockfile check, `--notice` checks for a newer CLI release:

- Source of truth: the tags of `https://github.com/driftsys/upskill`, read with
  `git ls-remote --tags`. `RemoteLookup` (`src/pipeline/check.rs`) resolves one
  ref only, so this needs a new tag-listing lookup and a test fake for it. Tags
  of the form `vMAJOR.MINOR.PATCH` count; others are ignored. _(Designer call:
  `git
  ls-remote` instead of the GitHub API, because the check code already
  uses it, it needs no new HTTP path and has no API rate limit.)_
- Frequency: at most once per 24 hours (`NETWORK_PERIOD_SECS`), across all scope
  roots. The time and the latest version found are stored in `notice.json` under
  a new top-level key. The reload-merge-save path (`notice::merge_roots`,
  `prune`) only knows per-root entries today, so it must be extended to keep
  that key. Writes go through the existing `notice.lock`.
- Run rules: the release line follows the same rules as the content lines. A
  busy or unavailable run lock means nothing prints. _(Designer call.)_
- Time budget: the release check has its own limit of 3 seconds, after the
  content lookups and their 5-second `NOTICE_TIME_LIMIT`. The whole run stays
  under the 30-second hook timeout. _(Designer call: a shared budget could
  starve the release check on a slow network every day.)_
- Audience: every user gets the `install.sh` line, whatever the install method
  (`cargo install`, package managers). No install-method detection. _(Designer
  call.)_
- Comparison: semantic version compare against the running binary's
  `CARGO_PKG_VERSION`. Only a strictly greater release prints.
- Line printed:
  `upskill <latest> is available (you have <current>): curl -fsSL https://raw.githubusercontent.com/driftsys/upskill/main/install.sh | sh`
- Once-only: the line prints once per latest version (the printed version is
  stored). With `--repeat` it prints at every run while the version is newer.
- Failure: a network error, timeout or unparsable tag list prints nothing and
  does not update the stored time, so the next run tries again.
- Opt-out: when the environment variable `UPSKILL_NO_UPDATE_CHECK` is set to a
  nonempty value, the release check is skipped. _(Designer call: needed for
  offline, CI and air-gapped use.)_
- `update --check` does not include the release check; it stays about content.

Known window: a tag exists a few minutes before its release binaries finish
uploading, so `install.sh` can still install the previous version in that
window. Accepted.

### D5. Building and publishing the plugin

`driftsys/metapowers` generates the plugin with `pack`, pinned to an upskill
release tag:

```sh
upskill pack upskill --source driftsys/upskill@vX.Y.Z --out plugins --catalog .
```

`pack` reads the bundle registry from the current directory; `--source` is only
validated and written into init-command text (`src/cli.rs`, `src/pack.rs`). So
the step runs from a checkout of upskill at the release tag, with `--out` and
`--catalog` pointing into a metapowers checkout (`--out` must be inside the
catalog root). _(Designer call: no remote fetching in `pack`; a checklist step
only.)_

```sh
cd upskill && git checkout vX.Y.Z
upskill pack upskill --source driftsys/upskill@vX.Y.Z \
  --out ../metapowers/plugins --catalog ../metapowers --force
```

`pack` names its outputs `<bundle>-claude` and `<bundle>-copilot`, which are the
paths of the hand-written directories in metapowers. The step overwrites them
with `--force`; the marketplace entries keep their `source` paths. Each upskill
release adds this step to its release checklist (`docs/` release notes or
`CONTRIBUTING`). _(Designer call: a manual step at first; automating it in
metapowers CI is follow-up work.)_

In this repository, `plugins/` stays: `pack` embeds its notice hook files in
every plugin with rules. It is no longer published as a standalone plugin.
`AGENTS.md` is updated to say so.

### D6. `install.sh`

After the existing `--version` line, the installer prints:

```text
Set up upskill in your AI client (skills and update notices):
  claude  plugin marketplace add driftsys/metapowers && claude  plugin install upskill@metapowers
  copilot plugin marketplace add driftsys/metapowers && copilot plugin install upskill@metapowers
opencode: upskill add driftsys/upskill --global --opencode
```

It prints on stderr, like the other installer messages. It runs nothing.

### D7. Docs

- Existing installs: users who installed the seven skills with
  `upskill add driftsys/upskill` get each skill twice once the plugin updates,
  and the old copy keeps the name `upskill-cli`. The release notes and
  `docs/book/getting-started.md` tell them to run `upskill remove` on those
  skills (with `--global` when installed globally). No code; no `doctor` check.
  _(User decision, 2026-11-25: docs note only.)_

- `docs/book/getting-started.md` and the README: the plugin is the first setup
  path; `install.sh` plus `upskill add` is the path for opencode and for users
  who want no plugin.
- `docs/book/commands.md`, `update --notice` section: the release check, its
  cache, its opt-out.
- A decision record that amends AD-0044 (standalone notice plugin replaced by
  the packed `upskill` plugin) and records approach 1.

## Tests (acceptance first)

- `cli_update_notice`: release check prints the line once for a newer tag, not
  for an equal or older tag, again with `--repeat`, nothing on network failure,
  nothing when `UPSKILL_NO_UPDATE_CHECK` is set, at most one remote call per 24
  hours (fake remote).
- `cli_pack`: packing `skills/upskill.bundle.yaml` produces a plugin named
  `upskill` with the seven skills and the setup hook entry for both clients.
- A script test for `upskill-setup.sh`: missing CLI prints the install message
  once per day; present CLI passes the notice through; output is valid JSON for
  each client; every failure exits 0.
- Rename: an `update` of a source that renamed `upskill-cli` removes the old
  install.

## Left to the builder

- Exact module placement of the release check (likely `src/notice.rs` plus the
  remote code in `src/pipeline/check.rs`).
- The `notice.json` key names.
- Whether the setup script and the existing notice JSON escaping share a file.
- The HOOK.md matcher form that gives Claude Code `startup` and Copilot CLI no
  matcher (a per-client matcher with only a `claude` key skips Copilot,
  `src/pack/hooks.rs`).
- opencode users running `upskill add driftsys/upskill` will see the existing
  "skipped 1 hook item(s)" line. Accepted.
