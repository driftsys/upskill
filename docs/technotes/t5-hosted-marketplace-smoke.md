# T5: smoke test of plugin output with a hosted git marketplace

Status: run on 2026-11-28; results recorded below. Binary: released `upskill`
0.9.7. Clients: Claude Code 2.1.308 and GitHub Copilot CLI 1.0.116, on macOS
(Darwin 24.6.0). Model of each client: `claude-fable-5-1` (Claude Code, from
`/context`) and `claude-sonnet-5.5` (Copilot CLI, as the client reported it).
Hosted marketplace: the private repository `driftsys/upskill-smoke` at commit
`1ebfe02`, packed with `upskill` 0.9.7.

Method: an agent ran most rows non-interactively (`claude -p` with stream-json
transcripts and debug logs; `copilot -p` with debug logs), with the isolation
that the checklist prescribes: `--scope local` from an empty project, a separate
`COPILOT_HOME` and a separate `TMPDIR` for each client. Where a command exists
only in an interactive session, the run used substitute evidence: for Claude
Code, the stream init event (and `claude plugin list`, `claude mcp list`) in
place of `/plugin`, `/skills`, `/agents` and `/mcp`, and `-p` with `--resume`
for `/clear`, `/compact` and `/context`; for Copilot CLI, `copilot skill list`,
`copilot lsp list` and `-p` agent listings in place of `/skills list`, `/agent`
and `/mcp`. The non-interactive Copilot run left four rows inconclusive: P4, P9,
P12 and V4. A person ran those four in an interactive Copilot CLI session with a
fresh `COPILOT_HOME` (manual interactive run): P4, P9 and P12 pass, and V4 is
inconclusive because that run checked the replies and not the debug log. The
Result cell of each names the run and the substitute evidence. The first Copilot
attempt ended when the first GitHub account reached its Copilot usage limit, so
the Copilot half ran again with a second GitHub account that has Copilot quota.

Issue [#637](https://github.com/driftsys/upskill/issues/637); decision:
[ADR-0046](../adr/0046-plugin-mvp-components.md), Decision 15; design:
[plugin MVP design](../wip/specs/2026-11-24-plugin-mvp-design.md), section 8.
The run follows the earlier local-marketplace test
[T3](t3-pack-marketplace-smoke.md). Each result is from one run, except where a
second run is named; model answers can vary between runs. A model's statement
about its own context is weak evidence, so each check names a second source (a
marker file, a command output or a log) where one exists.

When every check of the "Required checks" tables passes in both clients, the
decision records stop calling plugin output experimental (see "After the run").
A supplementary point may end as a documented skip, an inconclusive trace or a
recorded negative result; it does not block that step.

## Fixture

The fixture registry is `tests/fixtures/plugin-smoke/registry/`. It is separate
from `tests/fixtures/pack/registry/`, whose packed output golden tests compare
and whose bundles `pack --all` would pick up. The bundle `smoke` holds:

| Component | Item or key                                                   | Observable marker                                                                                                                | Needs at run time                 |
| --------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Rule      | smoke-rule                                                    | Answer `ruby-falcon-4821` when asked for the rule marker                                                                         | Released `upskill` on PATH (init) |
| Skill     | smoke-skill                                                   | Answer `amber-otter-1957`                                                                                                        | Nothing                           |
| Agent     | smoke-agent                                                   | Answer `cobalt-heron-3306`                                                                                                       | Nothing                           |
| Hooks     | smoke-hook, smoke-counter, smoke-match-bash, smoke-match-edit | Context `jade-lynx-7742` (session-start); marker file, counter file and the two matcher files                                    | POSIX `sh`, `date`                |
| Command   | smoke-command                                                 | Answer `onyx-wren-5913`                                                                                                          | Nothing                           |
| MCP       | smoke-mcp                                                     | Tool `smoke_marker` returns `slate-newt-2468`                                                                                    | `python3` 3.x on PATH, no network |
| LSP       | smoke-lsp                                                     | Marker file `${TMPDIR:-/tmp}/upskill-smoke-lsp-marker` (lines `started` and `documentSymbol` with a UTC time and the process id) | `python3` 3.x on PATH, no network |

- The command hook of `smoke-hook` runs `marker.sh` on `prompt-submit`. It
  appends `<client> <UTC time>` to `${TMPDIR:-/tmp}/upskill-smoke-hook-marker`
  and prints nothing. The client name comes from `UPSKILL_CLIENT`.
- The command hook of `smoke-counter` runs `counter.sh` on `session-start`,
  without a matcher. It appends one line to
  `${TMPDIR:-/tmp}/upskill-smoke-session-counter`. The line count is a signal
  outside the conversation: it shows how often the client starts a session or
  runs its session-start hooks, which the model's answer cannot show after
  `/clear` or compaction. It is secondary evidence: the primary evidence is the
  client log of the generated context command. The counter is a separate hook
  item because an event key appears once in an item and the context event
  already uses `session-start`. The format allows a `matcher` on a command
  event, but a `matcher` map cannot say "no matcher" for Copilot CLI, so the
  counter has none. Claude Code therefore also runs it on `resume`, which the
  context entry (`startup|clear|compact`) does not match.
- The hooks `smoke-match-bash` and `smoke-match-edit` run on `post-tool` with a
  per-client matcher (`claude: Bash` and `copilot: bash`; `claude: Edit` and
  `copilot: edit`). Each appends a line to
  `${TMPDIR:-/tmp}/upskill-smoke-match-bash` or `-match-edit`. They exist for
  check V5: a positive and a negative action for the Copilot CLI `matcher`.
  Copilot CLI documents `matcher` for `postToolUse` (specification, "Context
  hook limits"). The tool names `bash` and `edit` are unverified: no trial has
  used a `matcher`; the run records the names that the client reports.
- `pack` also adds the `upskill update --notice` session-start hook to the
  plugin of a bundle that has rules (`src/pack/hooks.rs`). It shows in the V3
  and V4 logs. In Copilot CLI it can add text to the first reply that asks the
  model to tell the user about updates. This is expected.
- The markers are two-word codes with a number, so that a model cannot give one
  by analogy with the file name.
- The MCP and LSP servers are inline `python3 -c` programs, because a plugin
  copies no other files for these keys. The LSP server appends `started` to its
  marker file when the client starts it, advertises `documentSymbolProvider`,
  appends `documentSymbol` and answers `[]` to `textDocument/documentSymbol`,
  and answers every other request with a `null` result. The LSP extension is
  `.smoke`, the language identifier `smokelang`.
- Locally, before the run, with `upskill` 0.9.7 built at commit `1e85763`:
  `upskill lint --strict tests/fixtures/plugin-smoke/registry/items` reports 8
  files checked and 0 findings, and linting the bundle file reports 0 findings.
  Linting the registry root checks only the bundle file (tracked separately as
  issue #663). The MCP and LSP programs from the packed JSON answered scripted
  exchanges (MCP: initialize and tool call; LSP: initialize, `documentSymbol`,
  an unknown request and shutdown) with exit code 0, and the hook scripts wrote
  their lines. The test `tests/cli_plugin_smoke_fixture.rs` pins the lint result
  and the `pack --all --catalog` output (both plugin directories, both
  marketplace files and the generated `init` text), so a format change that
  breaks the fixture fails in `just test`.

## Preparation

1. Create the hosted repository `driftsys/<repo>` (private is enough if both
   clients can clone it with the git configuration of the machine; the
   marketplace add commands below use the `owner/repo` form, which needs access
   through git or the client's GitHub login).
2. Copy the registry into a working directory and pack into it. `pack` runs in
   the registry root. `--source` must name the hosted repository, because the
   generated `init` command installs rules from that source. The registry and
   the packed output share one repository, as `driftsys/metapowers` does.

   ```sh
   work=$(mktemp -d)
   cp -R tests/fixtures/plugin-smoke/registry/. "$work"
   cd "$work"
   upskill pack --all --source driftsys/<repo> --out "$work/plugins" \
     --catalog "$work" --catalog-name smoke-market --catalog-owner driftsys
   ```

   Expected output: one `Wrote` line for each of `plugins/smoke-claude` and
   `plugins/smoke-copilot`, then one for each marketplace file.

3. Publish it. Run these commands only when you intend to create the repository:

   ```sh
   git init -b main && git add -A && git commit -m "chore: smoke test fixture"
   git ls-files
   git remote add origin <git url of driftsys/<repo>> && git push -u origin main
   ```

4. Use a clean state for each client so the run does not read earlier plugins:
   create one new empty project directory for each client (two directories) and
   change into the directory of the client under test
   (`mkdir /path/to/proj-x &&
   cd /path/to/proj-x`); run every command of that
   client from its directory. Before C1, run `upskill --version` and check that
   the `upskill` on PATH is 0.9.7 or later (the version that the local checks of
   this note used), and check that `claude plugin list` shows no `smoke` plugin
   at any scope and that `~/.claude/settings.json` does not set
   `disableAllHooks`: an inherited user setting or installation makes the run
   invalid, not a product failure. For Copilot CLI use a separate `COPILOT_HOME`
   (`export COPILOT_HOME=$(mktemp -d)`). For Claude Code use scope `local` in
   that project; every `claude plugin` command that changes configuration
   (marketplace add, marketplace remove, install, uninstall) passes
   `--scope local`, and every command runs in that directory. Remove the five
   marker files before each client (hook marker, session counter, LSP marker and
   the two matcher files): `rm -f "${TMPDIR:-/tmp}"/upskill-smoke-*`. Hooks and
   the LSP server run in the environment of the client, which can differ from
   your shell. If a marker file does not appear in your `${TMPDIR:-/tmp}`,
   search for it with
   `find /tmp /var/folders -name 'upskill-smoke-*' 2>/dev/null` and use that
   directory for every later `cat` and `wc -l`.
5. Record the checksums of `~/.claude/settings.json` before and after the run,
   as T3 did: identical before and after the Claude Code run (SHA-1 starting
   `e117cd7d`). Run no other Claude Code session during the run.

## Observations

- Claude Code cloned the private repository over HTTPS with the git
  configuration of the machine; Copilot CLI cloned it with the GitHub token of
  the account it ran with. The marker files of each client appeared in the
  `TMPDIR` given to that client process.
- Claude Code: the plugin cache directory of the installed plugin remains after
  uninstall and marketplace removal (plugin files, including `.in_use`). No
  setting or plugin record references it, so it is inert data.
- Claude Code: `-p` auto-allows `Read`, `Glob` and `Grep`, so a model can read
  `smoke-command` from the plugin cache without calling the Skill tool (C9b
  first run: a `find` with Bash, then `Read`). The refusal text is "Do not
  replicate this skill's workflow by other means — it is reserved for explicit
  user invocation." In the rerun the model obeyed it.
- Claude Code: `/context`, `/clear` and `/compact` work in `-p` mode with
  `--resume`. Every `claude -p` process fires `SessionStart:startup`, so the
  counter checks were taken around single calls. The `--resume` runs also fire
  `counter.sh`, which the checklist expects.
- `--project` works outside a git repository: the Copilot run used an empty
  project directory without `git init` and `upskill add --project` succeeded.
  The Claude Code runner ran `git init` first, which was unnecessary.
- Copilot CLI: after uninstall and marketplace removal, `plugin-data` keeps
  empty directories (`smoke-market/smoke` and `_direct/<hash>`), `settings.json`
  keeps `enabledPlugins` with `smoke@smoke-market` set to `false`, the file
  `installed-plugins.lock` is new and empty, and `config.json` gains
  `"installedPlugins": []`. `installed-plugins/` is empty. All of it is inert;
  compare with T3.
- Copilot CLI: a resumed prompt-mode session without folder trust ran no hooks.
  `--trust-folder` cannot be combined with `--resume`, so the resumed prompt of
  P8 used `COPILOT_ALLOW_ALL=true` (trusts the folder and approves all tools;
  the prompt was a one-word reply in an empty project).
- Copilot CLI: it honors `disable-model-invocation: true` for the skill tool and
  leaves the skills `smoke-command` and `init` out of the model's list. A model
  with a shell tool can still read the file and answer (P9b first run).
- The `upskill update --notice` session-start hook added an update line to the
  first Copilot reply ("upskill: 18 updates available (global)..."; the number
  comes from the cache of the real home directory, read only). The Claude Code
  run did not examine this hook separately.
- V5: Copilot CLI reported the tool names `bash` and `edit`, so the matchers
  needed no change. Counts per step: step 1 had one `bash` call (match-bash 0 to
  1, match-edit unchanged); step 2 had one `edit` call and one `grep` call
  (match-edit 0 to 1, match-bash unchanged). At the end of the Copilot run
  match-bash held 2 lines (the second from the `upskill add` shell call of the
  P12 substitute) and match-edit held 1. On the Claude Code side the hooks also
  matched `Bash` and `Edit` calls (informational).
- Claude Code final counts of its marker files: hook marker 19, session counter
  24, LSP marker 2, match-bash 3, match-edit 1.
- The `upskill add` of C12 and P12 left `.upskill-lock.json`, `CLAUDE.md`,
  `opencode.json` and `.vscode/settings.json` in the project, as T3 saw.

Locally verified with `upskill` 0.9.7 (commit `1e85763`): the generated `init`
command is `upskill add driftsys/<repo> smoke --kind rule --project --claude` in
the Claude Code plugin and the same with `--copilot` in the Copilot CLI plugin.
An `upskill add` of the fixture into a git project wrote
`.claude/rules/smoke-rule.md` and
`.github/instructions/smoke-rule.instructions.md`. Confirm that the model
reports the command output and runs no other command.

## After the run

When every required check passes in both clients (C1 to C15 and P1 to P14, which
cover the "Done when" observations of the issue), apply the closing items of
issue #637. ADR-0046, Decision 15, says that plugin output stays experimental
"until a smoke test with a hosted git marketplace passes in both clients, with
one component of each type, the `init` command and a generated catalog". This
note reads "passes" as every required check passing in both clients; a failed or
skipped required check keeps plugin output experimental. A supplementary point
may end as a documented skip, an inconclusive trace or a recorded negative
result, as the introduction states. Remove the word "experimental" for plugin
output from ADR-0044, ADR-0046, `docs/specification/specification.md` (the
paragraph of section 2.8, `pack`), `docs/book/support-levels.md`,
`docs/book/recipes.md` and `docs/book/commands.md`. Fill in the results of this
note and record the result in the issue.
