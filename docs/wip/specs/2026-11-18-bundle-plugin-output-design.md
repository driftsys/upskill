# Bundle plugin output: build a bundle as a client plugin

Date: 2026-11-18. Status: **design decisions agreed with the user on 2026-11-18;
not implemented**. Code baseline: `origin/main` at `0cec753`. This document
describes a first slice. It does not describe released behaviour.

Related records: [ADR-0003](../../adr/0003-generation-pipeline.md),
[ADR-0008](../../adr/0008-plugin-install-shellout.md),
[ADR-0013](../../adr/0013-agent-customization-targets.md),
[AD-0040](../../adr/0040-separate-customization-delivery-from-discovery.md),
[AD-0041](../../adr/0041-separate-client-representations-as-design-baseline.md),
[AD-0042](../../adr/0042-resteer-customization-delivery.md),

## Why

A user who wants the skills and subagents of a bundle in every project must run
`upskill add --global`. Claude Code and Copilot CLI each have a plugin system
that installs and updates such content for one user. A bundle author cannot
publish a bundle through those systems today without writing each plugin by
hand, as this repository does for `plugins/upskill-claude` and
`plugins/upskill-copilot`.

## What the user asked for

These statements come from the user on 2026-11-18.

1. A bundle can be built as a plugin.
2. The plugin serves the user install. A command of the plugin populates a
   repository with the project content.
3. Updates are reported or applied without a manual check.
4. Start with Claude Code and Copilot CLI. Codex follows later.

## Evidence from a hand-built prototype

On 2026-11-18 one plugin directory was built by hand from two skills of this
repository and one test agent, and loaded with `--plugin-dir` in Claude Code
2.1.308 and Copilot CLI 1.0.112. The plugin was not installed through a
marketplace. Each result is one model answer from one run.

| Check                                                | Claude Code                                     | Copilot CLI                                               |
| ---------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------- |
| `claude plugin validate`                             | passed; reports a missing README and LICENSE    | not applicable                                            |
| Skills from `skills/<name>/SKILL.md` are visible     | yes, named `<plugin>:<skill>`                   | yes                                                       |
| Agent from `agents/` is visible                      | yes, named `<plugin>:<agent>`                   | yes, named `<plugin>:<agent>`                             |
| Session-start hook text reaches the model            | yes (`hooks/hooks.json`, `additionalContext`)   | yes (root `hooks.json`, `additionalContext`)              |
| Each client reads only its own hook file             | yes                                             | yes                                                       |
| `commands/init.md` is visible                        | yes, as `/<plugin>:init`                        | yes, as the skill `<plugin>:init`                         |
| The init command ran its script                      | yes (`` !`...` `` with `${CLAUDE_PLUGIN_ROOT}`) | not completed: the run had no permission to use the shell |
| `${CLAUDE_PLUGIN_ROOT}` and `` !`...` `` are handled | yes                                             | no: the text reached the model unchanged                  |

Two results change the design:

- **Duplicate skills.** The host already had the same skills installed by
  `upskill add`. Claude Code listed both `upskill-cli` and
  `proto-bundle:upskill-cli`. A plugin and an `upskill add` install of the same
  skill give two exposures of one item.
- **Prefixed names.** Claude Code names a plugin skill `<plugin>:<skill>`. Text
  in a rule or a skill that refers to another skill uses the short name.

Not tested: installation from a marketplace, running the agent, the init command
in Copilot CLI to completion, MCP servers in a plugin, Codex.

## Goals

1. One command writes a plugin directory for Claude Code and a plugin directory
   for Copilot CLI from one bundle.
2. The plugin holds the skills and agents of the bundle and of its `requires`
   closure, generated by the existing generation pipeline.
3. The plugin holds an init command that installs the rules of the bundle into
   the current repository through `upskill add`.
4. The plugin holds the session notice hook, so the plugin does not depend on
   the `upskill` notice plugin.
5. Any number of installed plugins that hold the notice hook print a given
   notice once.
6. The bundle schema does not change.
7. upskill does not install, register or own the plugin. The user installs it
   with the client's own command, as for the `upskill` notice plugins (AD-0042,
   Decision 8).

## Non-goals

- A new `hook` item kind, `HOOK.md`, or any hook authored by a bundle. AD-0040
  and AD-0041 keep general hook authoring for a later scope. A later slice
  proposes it with its own decision record. The notice hook of section 5 is
  fixed text that `pack` writes; a bundle cannot change it.
- Codex, OpenCode and the VS Code editor.
- MCP servers and the third-party `plugins:` map of the bundle in the plugin
  output.
- Marketplace manifests and publication. The author copies the output to a
  marketplace repository, as `plugins/` is copied to `driftsys/metapowers`.
- Detection or repair of duplicate exposure between a plugin and an
  `upskill add` install.

## Design

### 1. Command

```text
upskill pack <bundle> --source <source> --out <dir> [--claude] [--copilot]
```

- `<bundle>` is a bundle name in the source registry of the current directory.
- `--source` is the `upskill add` source that the init command uses, for example
  `driftsys/upskill@v0.9.0`. The value is required and is written unchanged.
- No client flag writes both clients. The flags follow the existing client
  selection of `add`.
- `pack` is an author command, like `lint`, `fmt` and `new`. It reads no
  lockfile and writes only below `--out`. It refuses a non-empty output
  directory for a client unless `--force` is set.

### 2. Output: one directory for each client

```text
<out>/<bundle>-claude/
├── .claude-plugin/plugin.json
├── skills/<name>/SKILL.md (+ resources)
├── agents/<name>.md
├── commands/init.md
└── hooks/hooks.json

<out>/<bundle>-copilot/
├── plugin.json
├── skills/<name>/SKILL.md (+ resources)
├── agents/<name>.agent.md
├── commands/init.md
└── hooks.json
```

The prototype showed that one shared directory works for both clients. This
design writes two directories for three reasons. AD-0041 sets separate
representations for each client as the baseline. The agent file and the init
text differ between the clients. The layout matches `plugins/upskill-claude` and
`plugins/upskill-copilot`.

Manifest fields come from the bundle: `name`, `description`, `license`, and
`metadata.version` as `version`.

### 3. Content split

| Kind                 | In the plugin | Installed by init |
| -------------------- | ------------- | ----------------- |
| Skills (+ resources) | yes           | no                |
| Agents               | yes           | no                |
| Rules                | no            | yes               |

No tested client loads an always-loaded instruction file from a plugin. Init
installs rules only, so each item has one exposure for each client (AD-0041,
"one effective native exposure").

### 4. Init command

`commands/init.md` holds one fixed command line and the instruction to run it
and report its output:

```text
upskill add <source> <bundle> --kind rule --project --claude
```

The Copilot directory holds the same text with `--copilot`. The text does not
use `${CLAUDE_PLUGIN_ROOT}` or `` !`...` ``, because Copilot CLI passed both to
the model unchanged. The plugin ships no script. When the `upskill` binary is
missing, the command fails in the shell and the model reports the error.

This needs one addition to `add`: `--kind <kind>` (repeatable) restricts an
install to the given kinds. `search` already has a `--kind` filter.

A bundle without rules gets no init command.

### 5. Updates

The client's marketplace updates the plugin content.

Each plugin holds the session notice hook, which reports updates of the rules
that init installed. `pack` writes the hook definitions of
`plugins/upskill-claude/hooks/hooks.json` and
`plugins/upskill-copilot/hooks.json` unchanged. The hook calls
`upskill update --notice` and exits without output when the `upskill` binary is
missing. A bundle without rules gets no notice hook.

Several installed plugins, and the `upskill` notice plugin, can then run the
hook at the same session start. Today two runs that overlap both read
`notice.json` before either run saves it, and both print the notice. A run lock
in `update --notice` prevents this:

1. The run creates `<cache>/upskill/notice.lock` with create-only-if-absent
   semantics, before it reads `notice.json`.
2. The run that created the file does the check, prints the notice, saves
   `notice.json` and deletes the lock file.
3. A run that finds a lock file younger than 60 seconds prints nothing and exits
   with code 0. It makes no network request.
4. A run that finds a lock file of 60 seconds or older deletes it and continues
   from step 1. The check of one scope is limited to 5 seconds.

The lock covers only `update --notice`. Install, update and removal stay without
a writer lock (AD-0042, Decision 2).

### 6. Support level

`doctor` gains no new row in this slice. The user guide states that plugin
output is experimental until a maintainer runs a smoke test against both clients
with a marketplace install.

### 7. Code and tests

- A new library module builds the file list from the generation pipeline and
  returns data. `main.rs` writes the files and prints the result.
- Acceptance tests in `tests/cli_pack.rs` compare the output with golden
  directories for each client, and cover the refused non-empty output directory,
  a bundle without rules and a bundle with a `requires` closure.
- Acceptance tests for `add --kind` extend `tests/cli_add.rs`.
- Acceptance tests for the run lock extend `tests/cli_update_notice.rs`: a run
  with a fresh lock file present prints nothing, exits with code 0 and leaves
  `notice.json` unchanged; a run with a lock file of 60 seconds or older prints
  the notice; a completed run leaves no lock file.
- A test compares the hook definitions that `pack` writes with the files in
  `plugins/`.

## Known limits

- A user who has the plugin and works in a repository that holds the same skills
  from `upskill add` sees each skill twice.
- A reference to a skill by its short name inside a rule or a skill is not
  verified to resolve to the plugin skill `<plugin>:<skill>`.
- Copilot CLI 1.0.103 loaded a Claude registration by itself
  ([policy comparison](../../technotes/customization-delivery-policy-comparison.md)).
  An author who publishes both directories in one marketplace repository must
  check that Copilot CLI does not load the Claude directory.
- The init command and the notice hook need the `upskill` binary on the host.
- After a killed run leaves a lock file, two runs that start at the same time 60
  seconds or more later can both delete it and both print the notice.
- Two sessions in different repositories that start within the same seconds
  share the lock. One of them prints no notice until its next session start.

## Delivery order

1. Run lock in `update --notice`.
2. `add --kind`.
3. `upskill pack` for Claude Code.
4. `upskill pack` for Copilot CLI.
5. User guide and specification; smoke run with a marketplace install.

## Decisions

Decided by the user on 2026-11-18:

1. **Command name.** `upskill pack`, in place of the `build --plugin` form named
   earlier in the discussion.
2. **No schema change.** The discussion proposed a `package:` section in the
   bundle. Command flags carry the same information in this slice.
3. **Embedded notice hook with a run lock** (section 5). A plugin is standalone
   and does not depend on the `upskill` notice plugin.
4. **Two directories**, not one shared directory (section 2).
5. **ADR.** ADR-0013 states that a bundle and a native plugin package are
   distinct concepts. This slice keeps them distinct: a plugin is one output of
   a bundle. The implementation adds a decision record that states this.

## Alternatives considered

- **upskill installs the plugin through the client.** Rejected by AD-0042: the
  Claude plugin install rewrites user settings, and Copilot activated a Claude
  registration.
- **One shared directory for both clients.** Works in the prototype. Rejected
  for the reasons in section 2.
- **Init copies skills and agents into the repository as well.** Rejected: every
  user of the plugin would see each skill twice.
- **A script in the plugin runs the install.** Rejected: Copilot CLI does not
  expand the plugin root variable, and one fixed command line needs no script.
- **The notice hook only in the `upskill` notice plugin.** Rejected by the user:
  a plugin must work without a second plugin.
- **One marker file for each printed notice, without a time limit.** Rejected: a
  run that is killed after it writes the marker and before it prints loses that
  notice permanently.
- **The hook skips itself when the `upskill` notice plugin is installed.**
  Rejected: each client stores its plugins in a different way.
- **Remove duplicates by session id.** Rejected: not every client passes a
  session id to a hook.
- **Rules delivered by a session-start hook.** Deferred with the `hook` item
  kind. The prototype shows that the text reaches the model in both clients.
- **A new plugin schema, separate from the bundle.** Rejected: the bundle
  already holds the name, description, version, license, items and dependencies.
